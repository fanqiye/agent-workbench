## 三个改动及仍未解决的部分

**结束条件。** 小模型会在读完文档后直接输出自然语言，不调用嵌套引用数组的结束工具。现在既支持显式结束工具，也接受有证据的纯文本草稿：服务端重读已检索资料，核对授权、版本和原文，再附上来源。后者记录为 `validated_text_completion`，引用由服务端附加，不能说成模型主动选出了正确引文。原文能否支持草稿的全部语义仍需审核。

**金额。** 第一次模型把北区 12,000,000 分误说成总销售额 12,000,000 元。新增 `compare_revenue` 后，由代码使用整数分和 Decimal 计算：7 月 210000 元、8 月 186000 元，减少 24000 元；北区减少 30000 元，南区增加 6000 元，总体 -11.43%。代码要求两个月均覆盖所有地区，缺失数据不补成零。

第二次模型拿到了正确表格，自由文字仍出现“减少 240000 元”等错误。这是尚未解决的模型解释问题。界面把原稿折叠为需核对内容，优先显示核算表；不能声称回答准确率已经达标，也不能只展示成功状态。

**规划。** 第一次同时查询多个任务的时段，再使用过期候选，造成冲突。现在按阶段只开放适用工具：读日程 → 找一个任务的候选 → 选择候选 → 下一个任务 → 形成提案。服务端每次仍独立验证，而非只从提示词里隐藏工具。第二轮也有被拒绝的跨阶段调用，最终修正后形成合法草案。没有把错误步骤删除，也没有证明全局最优排程。

## 离线检查

运行 `python check.py`。13 组检查覆盖三条工具循环、确定性金额、SQL 越权/递归/大查询、CSV 整批回滚、跨租户和角色读取、伪造引文、撤权、资料变化、时区缺失、日程冲突、重复审批、UTF-8 日历折行、模型不可用、取消、工具注入、预算以及实际 HTTP 的 Host/Origin/nonce。

其中模型为脚本替身，数据在临时目录，不能用它们证明模型准确率。SQLite SQL 拒绝还包括 DROP、UPDATE、ATTACH、PRAGMA、系统表、扩展加载、多语句；这是工具权限检查，不是“提示注入已全部解决”的证明。

## 六分钟演示

1. 资料核查：提一个退款问题，展开来源行号，再问文档里没有的报销标准。解释权限过滤与回答正确性是两回事。
2. 经营分析：比较两个月，先看核算表，再展开 SQL。解释为什么正确的查询结果也可能被模型说错，以及为什么原稿没有自动成为业务报表。
3. 个人安排：给出三项任务，查看选时段和拒绝轨迹。核对时间后确认，下载本机 ICS；说明未向任何日历账号写入。
4. 最后跑离线检查，选一个越权 SQL 或日程冲突检查解释代码；不要把所有文件名背一遍。

## 面向真实使用的缺口

文档检索仍是关键词匹配，三篇样例不足以代表企业知识库。分析器只支持一张受限聚合表，不是任意数据库的 NL2SQL 平台。规划只有显式 UTC 偏移和小规模任务，不处理夏令时规则与重复日历。没有多用户认证、跨机器 worker、后台定时任务、语音、邮件发送或个人账号授权。

正式接入前应由实际业务决定投入方向：资料产品补真实脱敏语料和独立标注；分析产品补指标口径与经审阅的语义层；个人产品补本人真实窗口、日历读取授权和试用反馈。不要为了仓库数量重复造相同的聊天壳。
